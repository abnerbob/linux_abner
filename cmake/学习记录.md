七、cmake编排
ExternalProject_Add调用原生cmake外部模块时候，可以USES_TERMINAL_BUILD设置成1(将外部项目的构建过程直接挂载到当前终端的控制权下 不理解先记录)
调用原生cmake外部模块，可以使用Jobserver 机制(共享并发令牌)

ExternalProject_Add调原生和非原生的cmake工程，其实本质上还是用了子工程的增量编译来感知更新。

3.add_subdirectory (或 FetchContent) 模式
直接添加原生cmake工程子目录的方式，target直接解析到上层cmake中，编译由上层cmake统一调度。
工具链和配置项使用上层cmake工程。
不适用异构(不同工具链，不同平台)组件。

4.add_custom_target
原生接口，执行指定的target，可以用来执行外部组件的编译和特定任务
调试过程中，target中的每个任务都会顺序执行，复杂执行流程会很尴尬。
无法感知组件内部的更新，但每次执行make target都会执行。

八、include_guard
include_guard(GLOBAL)：
作用：在整个构建树（Global Build）中只执行一次。
场景：适用于全局单例的配置，比如定义全局工具函数。
include_guard(DIRECTORY)：
作用：在当前目录及其子目录的作用域内只执行一次。
include_guard() (不带参数)：
作用：默认行为。它取决于当前的变量作用域。

PRIVATE（私有）： 仅当前目标使用，不传递给依赖方。
PUBLIC（公开）： 当前目标使用，并传递给依赖方。
INTERFACE（接口）： 当前目标不使用，仅传递给依赖方。

A. 粗粒度排查：message 打点
这是最原始但也最有效的手段。在怀疑的代码段前后打印时间戳：
string(TIMESTAMP START "%S" UTC)
# ... 怀疑很慢的代码 ...
string(TIMESTAMP END "%S" UTC)
message("Duration: ${END} - ${START} seconds")

B. 细粒度排查：variable_watch
如果你怀疑某个全局变量被频繁修改导致逻辑变慢，可以监控它：
variable_watch(CMAKE_C_FLAGS) # 只要这个变量一变，CMake 就会打印调用栈

--trace-expand：看逻辑（为什么 if 没进去？变量为什么是空的？）。

--profiling-output：看时间（为什么配置要这么久？）。
cmake .. --profiling-output=perf.json --profiling-format=google-trace
打开 Chrome 浏览器，输入 chrome://tracing。
把生成的 perf.json 拖进去。
你会看到一个类似逻辑分析仪的时间轴（Timeline），它会清晰地标注出哪个 find_package 耗时最久，哪个 add_subdirectory 拖了后腿。

循环依赖：
理论上：有向无环图（DAG）不允许循环依赖。 如果 A 依赖 B，B 又依赖 A，构建系统会陷入“谁先编译”的死循环。
CMake 的处理：
静态库（Static Libs）：CMake 允许链接层面的循环依赖。链接器在处理静态库时，可以通过多次扫描（--start-group ... --end-group）来解析互相引用的符号。
动态库（Shared Libs）：严格禁止。在 Linux/Windows 下，动态库必须在链接时确定所有符号（或者至少知道去哪找），循环依赖会导致链接失败。
